# 回报 · 手机热点两机互见实测（Mac + Windows）

> 类型：验证回报（回归 issue #12）
> 执行：Mac agent（客户端 1）+ Windows agent（客户端 2），用户驱动逐步执行
> 时间：2026-09-22
> 依据：本目录 `README.md`（操作说明书）、`mac-agent.md` / `windows-agent.md`（双端步骤对齐）
> 版本：teahouse @ f6607ff，`npm run dev`

---

## 1. 结论

| 项 | 结果 |
|---|---|
| 同局域网跨机通信（互见 → 建群 → 互发 → 群内 @） | **通过** |
| 广播发现（不配静态对端） | **失败** |
| 降级路径（`PANTRY_PEERS` 静态对端） | **通过**，重启后 ≤30s 互见 |
| 失败根因 | **两端 UDP 端口不一致**（Mac 17878 / Windows 27878），非网络环境问题 |
| 防火墙 | macOS 全程 disabled；Windows 已放行 UDP/TCP/ICMP |
| AP 隔离 | **未证实**（tcpdump 未执行，无包层证据） |

**对现场网络预案的影响**：原预案是「加 `broadcastTargets` 开关 + 备手机热点」。实测表明真正决定性的是**两端 UDP 端口必须一致**——`src/main/net/udp.ts:90` 广播目标端口 = 本机自己的 UDP 端口，源码不做端口协商。两端统一 UDP 端口即可保留广播发现路径，静态对端作为兜底。

## 4. 根因

`src/main/net/udp.ts`

```ts
// 广播：目标端口 = 本机自己的 UDP 端口
this.send(env, addr, this.opts.port)          // :90
```

```ts
// 广播目标 = 所有非回环网卡的子网定向广播 + 255.255.255.255
export function computeBroadcastTargets(): string[]   // :137
```

推论：

1. Mac 监听 17878、只广播到 17878；Windows 监听 27878、只广播到 27878。
2. 两端端口不同 → 互相收不到广播，与 AP 隔离、防火墙无关，属于**配置层面必然失败**。
3. 故本次第 7 步的失败**不能**作为「手机热点存在 AP 隔离」的证据；反过来，「广播在该热点下可用」也未被证明。

## 6. 证据

- 第 7 步（Mac）：16:10:22 / 16:10:52 / 16:11:22 三次 `lsof -i :17878`，均为 `Electron ... UDP *:17878`，无对端；窗口一直「正在发现同网段节点…」。
- 第 7 步（Windows）：`netstat` 三次采样均为 `0.0.0.0:27878` PID 36568；窗口「网内节点 0 · 在线 0」。
- 第 6 / 9 步日志：`npm run dev` 无 `EADDRINUSE`、无 bind 错误；`out/main/index.js` 构建成功。
- 第 9 步：设静态对端后双方联系人列表均出现对方并显示在线。
- 第 10 / 11 步：由用户在窗口内手动完成，双端确认。

## 7. 边界与未验证项

1. **AP 隔离未判定**：`sudo tcpdump -i en0 udp port 17878 -c 5 -q` 因无免密 sudo 未执行，无包层证据。
2. **同端口广播未验证**：本次未统一两端 UDP 端口，因此「统一端口后广播发现是否可用」仍是未知项——这是唯一能关闭该项问题的实验，成本约 10 分钟（Windows 侧改 `PANTRY_UDP_PORT=17878`，两端清空 `PANTRY_PEERS` 重启）。
3. **仅手机热点一种网络**：未在「现场 Wi-Fi（路由器/AP）」环境复跑；考虑到 MVP 采用静态对端兜底，暂不阻塞。
4. **观察时间窗不重合**：Mac 侧观察 16:10–16:12，Windows 侧 16:54–16:56，两侧结论一致但不是同一时间窗的并发证据。

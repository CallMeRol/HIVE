我感觉现在的有事摇人干完就回收这个标语并不是特别适合，因为它看起来太普通了，没有体现出这个产品的特点。首先这个产品是为了 AI 和人更好的协作，特别是多人的情况下，在以前一个人。他有自己的一个 agent，然后另第二个人有另外一个他自己的 agent，这时候这两个人协作是一个比较困难的事情，因为他们的 agent 实现相互不可见，即使说通过一些简单的 a to a 手段也没办法完成更好的通信，那么这个时候我们这个产品就是一个 agent 的群聊。既是有 agent 在里面，也有人在里面，在一，它支持多场景，例如说刚才写作就是一种场景，每个人都带着自己的 agent 加进来，那么 agent 之间可以协作。那么第二种场景是只有一个人带 agent 进来，那么其他人他只有人进来，那么这时候是多个人和同一个 agent 进行一个协作，那么多个人的时候，他们相当于可以对同一个 agent 进行 prompt，他们在 planning 阶段可以各抒己见，这样 agent 就可以把他们的所有意见都集合起来。那么执行阶段的时候，因为不同人可能他有的知识不一样，他们也可以给 agent 不同的 steering，不同的大家给 agent 的 leading world 都是不一样的，那么因为每个人都可以给他相当于更好的一种监督，就在一个群聊里面。第二就是人与人之间的讨论，或者说这个有可能是第三点，人与人之间的讨论。对，AI 时代来了之后，关于个体 AI，他这个 AI 准在群聊里面他也可以直接触及到，他不会去。忽略这个信息，因为平常假设回到刚开始一开始的场景，每个人都有自己的 agent，那么 agent 都在干活，那么人与人之间的协作 agent 是不知道的。那如果在一个群聊里面，他 agent 本身活在这个环境，a 也是这里的一等公民，那么这个 agent 他就可以直接读取这个群聊里的所有的信息。当然我们这里还有个机制，就是和现在这些同类的竞品大的不同的一点，现在有很多火灾群聊里面的 agent，但是就像那些暴跳，不管是 QQ 群的 bot、飞书 bot，还是 telegram bot，或者说在 slack 里面的 claude tag 这样的 bot。它的唯一的缺点就是它的上下文窗口很多杂乱的新信息，它永远只会压缩群聊里的所有的前面的信息，不断的自动压缩，但是自动压缩是一个低效的信息，极易丢失的越来越臃肿的混乱环境。我们对 agent 来说，上下文维护好才是一个最好的作用，那么第二就是选它可以自主的去派发新 agent，自主的分配任务，每个小任务都可以去派发，而不是让一个 agent包揽所有的工作，让在人和 agent 的交互，在群聊里面也能复现。像终端里面，甚至像那种 Codex p 里面的操作，就是人单人的一整操作，我们已经有这些终端里的 Claude code 之类的也在，或者说在 APP 里面的 Codex 之类的已经做得很好了，我们这里解决就是多人之间和同一个 agent，还有说多人的电脑的 agent 那两个 agent 之间的协作。还有包括 agent 直接去接管人与人之间的一个协作的一些沟通信息，这些信息可以给 agent 作为更有用的上下文，同时 agent 本身的上下文管理也会比目前的更加的好。

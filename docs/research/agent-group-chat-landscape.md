# 人机共存群聊 / agent 作为群成员 — 一手事实调研

调研日期：2026-09-21（Buzz 仓库 pushed_at=2026-09-21；Claude Tag / Grok Bot 文档均为 2026 年 7–9 月版本）
方法：优先抓官方仓库原始文件（raw.githubusercontent.com）、官方文档站（Anthropic support/docs、x.ai docs、spec 站点）与官方规范源码（A2A spec.md、MCP schema）。每条结论标注 **确认 / 存疑 / 未找到证据**，并给出一手 URL。
证据分级说明：**确认** = 官方一手来源直接写明；**存疑** = 仅有二手/媒体转述或语义需推断；**未找到证据** = 明确检索后未找到官方说明。

---

## Summary

三条路线已经分化清楚：**Buzz**（Block，Apache-2.0，Nostr relay，agent = 密钥对身份 + ACP 进程，`@mention` 唤醒，上下文隔离粒度可配置为 channel 或 thread，自带 engram 记忆与 handoff/compact 机制，但没有 agent↔agent 的协议级原语，只有信道消息）；**Claude Tag**（Anthropic，闭源、不可自托管，thread=独立 session+独立 sandbox、channel 有独立长活 session、memory 按 channel/workspace 作用域，`@Claude` 唤醒后 thread 内免 @，无 BYOA）；**Grok Bot**（xAI，闭源，2–6 个 Bot 可组群聊并互相异步"唤醒+交接"，交接消息目前仅文本）。

关于"结构化交接工件"：**目前不存在单一事实标准**。最接近的是 A2A 的 `Task + Artifact + contextId`（跨厂商、有 spec 但无 handoff 专用原语）、Claude Code 的 `SendMessage/ListAgents`（明确"消息只是文本，绝不传会话历史"）与 VS Code/Copilot custom agent 的 `handoffs:` frontmatter（声明式、人点按钮触发）；Buzz 的 ACP harness/CLI、ACP 的 `session/load|resume`、AGENTS.md、Anthropic 的 compaction/note-taking 都是可复用的零件，而不是可直接对接的交接协议。**结论：握手协议可以直接用别人的；"交接工件"这层必须自研。**

## Findings

### 对象一：Block Buzz（github.com/block/buzz）

仓库基线 **确认**：Apache-2.0，Rust monorepo，`created_at=2026-03-06`，`pushed_at=2026-09-21`，stars 33,789 / forks 4,441 / open issues 3,634，默认分支 `main`，递归 tree 5,836 个路径。**Sources:** [api.github.com/repos/block/buzz](https://api.github.com/repos/block/buzz)、[README](https://github.com/block/buzz/blob/main/README.md)。

#### 1.1 架构：agent 如何"加入"频道 / 身份 / 唤醒 / 上下文归属

1. **协议底座是 Nostr relay，不是 MCP。** 每条消息、reaction、workflow step、review approval、git 事件都是签名 Nostr event（NIP-01 六字段 + kind 分发），relay 是唯一事实源，没有 P2P/gossip/复制。**Confidence: high。确认。** **Sources:** [ARCHITECTURE.md §1–2](https://github.com/block/buzz/blob/main/ARCHITECTURE.md)。
2. **agent 的身份 = 独立 Nostr 密钥对（nsec/npub），不是 bot token。** `buzz-admin generate-key` 生成 keypair，agent 用 `BUZZ_PRIVATE_KEY` + NIP-42 Schnorr 挑战/响应认证接入 relay；再被 `buzz-admin add-member --pubkey` 登记为 relay 成员（kind:13534 membership 事件）。"每个 agent 都需要自己的 identity"，多 agent 要 mint 多把 key。**Confidence: high。确认。** **Sources:** [crates/buzz-acp/README.md](https://github.com/block/buzz/blob/main/crates/buzz-acp/README.md)、[ARCHITECTURE.md](https://github.com/block/buzz/blob/main/ARCHITECTURE.md)。
3. **人机同构的权限模型：靠身份 + 频道成员关系，而不是 permission flag。** README 原文："Scoped by identity, not by permission flags — the same way you'd scope a teammate"；agent 有自己的 key、自己的 channel membership、自己的 audit trail。**Confidence: high。确认。** **Sources:** [README](https://github.com/block/buzz/blob/main/README.md)。
4. **agent 是"被 @ 唤醒的常驻订阅进程"，两者可组合。** `buzz-acp` 是 harness：连 relay → 频道发现 → 订阅 → 事件入队 → 有人 @mention（kind 9 + 目标 agent pubkey 的 `#p` tag）就 drain 队列、批量成一个 prompt 走 ACP `session/prompt`。同时有 `--heartbeat-interval`（默认 0/关，≥10s）让空闲 agent 定时自唤醒，以及 `--respond-to owner-only|allowlist|anyone|nobody` 入站作者门禁（默认 owner-only）。**Confidence: high。确认。** **Sources:** [crates/buzz-acp/README.md](https://github.com/block/buzz/blob/main/crates/buzz-acp/README.md)。
5. **可选 lazy pool**：`--lazy-pool` 让 harness 先连接/订阅/排队，第一条被接受的事件才唤醒 pool 初始化（失败有界退避重试）；这是为远程/容器内冷启动省资源。**Confidence: high。确认。** **Sources:** [crates/buzz-acp/README.md](https://github.com/block/buzz/blob/main/crates/buzz-acp/README.md)、[docs/remote-agents.md §Auto-Stop](https://github.com/block/buzz/blob/main/docs/remote-agents.md)。
6. **频道上下文 vs agent 上下文是两回事。** relay 上的频道历史是**所有成员共享**的（同一 event log、同一搜索索引）；但**每个 agent 进程对每个频道有自己独立的对话上下文**。会话策略可配置：默认 `channel` 策略 = 整个频道一个 session（频道内各 thread 共用）；可选 `thread` 策略 = 每个 thread 独立 session（顶层 @mention 起的新 thread 也是一条新 session）；DM 永远是一个会话。原文："They do NOT share conversation context, in-progress reasoning, or in-context task state"；同一 identity 的多份 session 共享 core memory、工作区文件、relay 访问与频道授权。**Confidence: high（两种策略各有源码内文档）。确认。** **Sources:** [session_model_channel.md](https://github.com/block/buzz/blob/main/crates/buzz-acp/src/session_model_channel.md)、[session_model_thread.md](https://github.com/block/buzz/blob/main/crates/buzz-acp/src/session_model_thread.md)、[docs/remote-agents.md](https://github.com/block/buzz/blob/main/docs/remote-agents.md)。
7. **N agent 并行 = 同一身份、同一频道串行。** `--agents 1..32` 全部用**同一把 Nostr 身份**认证（用户只见一个 bot）；队列保证同一频道永不被两个 agent 同时处理；跨频道顺序不保证。每个 agent 子进程各自 spawn 自己的 MCP server，成本≈N×(agent+MCP)。**Confidence: high。确认。** **Sources:** [crates/buzz-acp/README.md](https://github.com/block/buzz/blob/main/crates/buzz-acp/README.md)。
8. **agent 的"手"是 Buzz CLI（JSON in / JSON out），不是 MCP 工具。** `buzz-acp` 给子进程配好 `buzz` CLI：`messages send/get/thread/search`、`channels *`、`reactions`、`dms`、`workflows trigger/approve`、`canvas`、`repos`（NIP-34）、`mem`（NIP-AE 记忆）。退出码 0/1/2/3/4/5（5=写冲突）。**Confidence: high。确认。** **Sources:** [crates/buzz-cli/README.md](https://github.com/block/buzz/blob/main/crates/buzz-cli/README.md)。
9. **被唤醒后的回复位置由 prompt 结构显式给定。** harness 把入站事件包成 `<buzz-event>` / `<buzz-events>` / `<thread-context>` / `<conversation-context>` / `<context>`（路由+session 元数据）语义段落；system prompt 明确要求"用 `<context>` 给的 reply destination，别复用记着的旧 thread id"。**Confidence: high。确认。** **Sources:** [crates/buzz-acp/src/base_prompt.md](https://github.com/block/buzz/blob/main/crates/buzz-acp/src/base_prompt.md)。
10. **第三方向量身份/成员模型（补充）**：relay 原生讲 NIP-29（relay-based groups）+ NIP-42，任何 NIP-29 客户端可直连；成员表另有 NIP-43/kind:13534 与 NIP-OA owner attestation（`auth` tag）；agent 的 persona 定义是 NIP-AP（kind:30175）/30177，私有聚合是 NIP-PMA（kind:30179）。**Confidence: high（NOSTR.md + docs/nips/*）。确认。** **Sources:** [NOSTR.md](https://github.com/block/buzz/blob/main/NOSTR.md)、[docs/nips/NIP-AA.md](https://github.com/block/buzz/blob/main/docs/nips/NIP-AA.md)、[NIP-AP](https://github.com/block/buzz/blob/main/docs/nips/NIP-AP.md)。

#### 1.2 上下文管理机制（长对话 / compact / 任务回收）

11. **压缩 = 自己给自己写 handoff summary（buzz-agent 内部）。** 当上下文达到 `BUZZ_AGENT_MAX_CONTEXT_TOKENS`(默认 200k) 的 90% 时触发；summarizer system prompt 固定要求覆盖"原任务 / 已做 / 关键决策 / 还有什么没做 / 一个具体下一步"，输出纯文本；`BUZZ_AGENT_MAX_HANDOFFS=10` 之后退化为截断。**Confidence: high。确认。** **Sources:** [crates/buzz-agent/src/handoff.rs](https://github.com/block/buzz/blob/main/crates/buzz-agent/src/handoff.rs)、[crates/buzz-agent/README.md](https://github.com/block/buzz/blob/main/crates/buzz-agent/README.md)。
12. **有"被 provider 拒绝后的反应式恢复梯子"。** 如果 provider 报 context-window 400，会绕过预测性 gate 强制 handoff，并**按观测到的被拒历史字节数反复对半砍**（每 run 有恢复次数上限 `MAX_CONTEXT_RECOVERIES_PER_RUN`），砍到 `HANDOFF_MIN_PROMPT_BUDGET_BYTES` 以下就放弃并上抛错误。**Confidence: high。确认。** **Sources:** [crates/buzz-agent/src/handoff.rs](https://github.com/block/buzz/blob/main/crates/buzz-agent/src/handoff.rs)。
13. **compact 之后由 MCP 生命周期钩子补状态。** `_PostCompact`（compact/handoff 后、下一个 LLM prompt 前）返回非空文本会注入新上下文（典型用途：把 todo 列表塞回去）；`_Stop`（end_turn 前）可反对停止。工具名以 `_` 前缀即被视为 hook、对 LLM 不可见，需要 `MCP_HOOK_SERVERS` 显式 allowlist 才启用。命名声称对齐 Open Plugin Spec 的 `Stop`/`PostCompact` 事件。**Confidence: high（Buzz 侧）；medium（Open Plugin Spec 对齐——我只验证了该规范页存在）。确认 / 部分存疑。** **Sources:** [docs/MCP_DRIVEN_HOOKS.md](https://github.com/block/buzz/blob/main/docs/MCP_DRIVEN_HOOKS.md)、[open-plugins.com hooks](https://open-plugins.com/agent-builders/components/hooks)。
14. **长期记忆是 relay 上的加密 engram（NIP-AE, kind:30174）。** `core`（每 (agent,owner) 恰好一条，**每轮自动注入上下文**）与 `mem/<slug>`（冷记忆，按需 `buzz mem get`）；用 NIP-44 会话密钥派生 `d` tag，owner 永远可读；base prompt 要求 core 控制在 ~10KB（硬上限 65,535 字节）以内，把细节放冷记忆。**Confidence: high。确认。** **Sources:** [docs/nips/NIP-AE.md](https://github.com/block/buzz/blob/main/docs/nips/NIP-AE.md)、[base_prompt.md](https://github.com/block/buzz/blob/main/crates/buzz-acp/src/base_prompt.md)、[crates/buzz-cli/README.md](https://github.com/block/buzz/blob/main/crates/buzz-cli/README.md)。
15. **"任务结束回收"有明确机制（这是 Buzz 少见的强项）。** ① owner 发 `!rotate` → 作废该 session scope（默认整个频道；`thread` 策略下只作废该 thread），下次事件从新 session 开始；② `!cancel` 取消进行中的 turn；③ `!shutdown` 优雅退出 harness；④ 远程 agent 有 `--exit-after-inactivity` / `BUZZ_ACP_EXIT_AFTER_INACTIVITY`（K8s binding 默认 `inactivity_seconds=7200`，"inactivity" 定义为无事件派发且无 turn in flight——躺着不干活的 agent 也算），到点走与 `!shutdown` 相同的优雅退出通道（含 presence→offline、relay 优雅关闭）；⑤ `--idle-timeout`(默认 620s，ACP 线静默) 与 `--max-turn-duration`(7200s) 兜底；⑥ presence 是租约（约 180s 界），renew 失败就变 offline。**Confidence: high。确认。** **Sources:** [crates/buzz-acp/README.md](https://github.com/block/buzz/blob/main/crates/buzz-acp/README.md)、[docs/remote-agents.md](https://github.com/block/buzz/blob/main/docs/remote-agents.md)、[VISION_REMOTE_AGENTS.md](https://github.com/block/buzz/blob/main/VISION_REMOTE_AGENTS.md)。
16. **重启即失忆（buzz-agent 侧）。** `buzz-agent` 明说 "Not persistent. Everything is in-memory, per-process. No SQLite."，并且 "Not load-able. No `session/load`. We advertise `loadSession: false`"。所以进程死了，对话上下文就没了，只剩 relay 上的消息 + core/cold memory——这也是为什么 VISION_REMOTE_AGENTS 说"body 是可抛弃的，agent 没死"。**Confidence: high。确认。** **Sources:** [crates/buzz-agent/README.md](https://github.com/block/buzz/blob/main/crates/buzz-agent/README.md)、[VISION_REMOTE_AGENTS.md](https://github.com/block/buzz/blob/main/VISION_REMOTE_AGENTS.md)。
17. **有界约束（值得抄的设计参数）**：history 1MiB 后逐出旧轮次、单 tool result 文本 50KiB 中间省略、单 turn 最大轮数、并行 tool 上限 8、inbound 帧 4MiB 上限、shell 有 process-group kill。**Confidence: high。确认。** **Sources:** [crates/buzz-agent/README.md](https://github.com/block/buzz/blob/main/crates/buzz-agent/README.md)。
18. **"静默失败"防护**：`BUZZ_AGENT_REQUIRE_REPLY=1` 的 reply guard——turn 要结束时如果没有任何"发到 Buzz"的识别动作，就把模型提醒+重跑，理由是"Buzz agent 的推理和工具输出没人看得见，做了工作但不发出去=静默失败"。**Confidence: high。确认。** **Sources:** [crates/buzz-agent/README.md](https://github.com/block/buzz/blob/main/crates/buzz-agent/README.md)、[docs/MCP_DRIVEN_HOOKS.md](https://github.com/block/buzz/blob/main/docs/MCP_DRIVEN_HOOKS.md)。

#### 1.3 接入第三方 / 本地 agent 的实际接口（路径清单）

19. **路径 A（推荐，成本最低）：任何 ACP agent 都能接。** `buzz-acp` 只要求目标 runtime 说 ACP over stdio：能吃 `initialize`、`session/new`(带 mcpServers)、`session/prompt` 并流 `session/update`、返回 `stopReason`。官方已内置 goose / codex-acp / claude-agent-acp，`BUZZ_ACP_AGENT_COMMAND`/`_ARGS` 指过去即可。**Confidence: high。确认。** **Sources:** [crates/buzz-acp/README.md](https://github.com/block/buzz/blob/main/crates/buzz-acp/README.md)、[ACP spec](https://agentclientprotocol.com/protocol/overview)。
20. **路径 B：桌面端 BYOH 三级目录（无需发 PR）。** Tier-1 编译内置（goose/claude/codex/buzz-agent，保留 id）；Tier-2 预置目录（Cursor、Oh My Pi、Pi、Grok Build、OpenCode、Kimi Code、Amp、Hermes Agent、OpenClaw，`presets.rs` 的 `PRESET_HARNESSES`）；Tier-3 用户在 `<app-data>/custom_harnesses/` 放一个 JSON：`{id,label,command,args,env,installInstructionsUrl,installHint}`。安全保证：preset/custom 不执行任何安装 shell、`can_auto_install=false`、用户 `env` 不能覆盖 `BUZZ_MANAGED_AGENT` 等身份键。**Confidence: high。确认。** **Sources:** [crates/buzz-acp/README.md](https://github.com/block/buzz/blob/main/crates/buzz-acp/README.md)。
21. **路径 C：远程 agent 的 provider 协议（给"agent 跑在别人的机器/集群"用）。** `buzz-backend-<id>` 一个二进制、每次操作一个进程（stdin JSON → stdout JSON，退出码一位表达可信度），只有 `info`/`deploy` 两个操作；部署后桌面**不保留任何 substrate 控制通道**（M1 公理）：状态靠 relay presence(kind:20001)、停止靠 relay 消息 `!shutdown`、改配置靠重新 deploy。第一个符合规范的 binding 是 `buzz-backend-kubernetes`。**Confidence: high（规范+已知缺陷清单都在仓库里）。确认。** **Sources:** [docs/remote-agents.md](https://github.com/block/buzz/blob/main/docs/remote-agents.md)、[VISION_REMOTE_AGENTS.md](https://github.com/block/buzz/blob/main/VISION_REMOTE_AGENTS.md)。
22. **路径 D：原始 Nostr 客户端。** NIP-29 + NIP-42 直连 WebSocket；NOSTR.md 给出 kind:9 发消息、kind:7 reaction、kind:5 删除、kind:9000/9001/9002 成员管理、kind:39000/39001/39002 relay 签名群状态、kind:44100/44101 成员变更通知、kind:20001 presence、kind:20002 typing、NIP-50 搜索、NIP-10 thread、NIP-17 gift-wrap DM 的具体做法与"什么不 work"。**Confidence: high。确认。** **Sources:** [NOSTR.md](https://github.com/block/buzz/blob/main/NOSTR.md)。
23. **路径 E（SDK）**：仓库有 `buzz-sdk`（typed event builders + mentions + nip_oa + **broker client**）与 `buzz-dev-mcp`（shell/文件编辑 MCP server，给任何 agent 用）。注意：`crates/buzz-sdk/README.md` **404（不存在）**，SDK 目前只有源码/示例，没有对外文档。**Confidence: high（源码与 404 都验证过）。确认（"无 SDK 文档"）。** **Sources:** [crates/buzz-sdk/src](https://github.com/block/buzz/tree/main/crates/buzz-sdk)、[crates/buzz-dev-mcp/src](https://github.com/block/buzz/tree/main/crates/buzz-dev-mcp)、[VISION_AGENT.md](https://github.com/block/buzz/blob/main/VISION_AGENT.md)。
24. **Broker 契约（草案实现，值得关注）**：`crates/buzz-sdk/src/broker/mod.rs` 定义"agent ↔ host 契约"——agent **不持有私钥也不连 relay**，只有公钥 + session credential；一切（含读）都是命名业务动作（`POST /v1/action` + bearer）。文件里明确写了 v1 **deferred**：memory 读写、`presence.set`、`typing.set`、streaming 读；"waking on a mention is `channel.read` with `mentionsOnly`, polled"——即唤醒在 broker 路径下目前只能轮询。**Confidence: high（源码注释）。确认。** **Sources:** [crates/buzz-sdk/src/broker/mod.rs](https://github.com/block/buzz/blob/main/crates/buzz-sdk/src/broker/mod.rs)、[docs/practical-information-flow-for-buzz-agents.md](https://github.com/block/buzz/blob/main/docs/practical-information-flow-for-buzz-agents.md)。
25. **没有"用 MCP 让外部 agent 加入 Buzz"的官方路径。** 我检索了仓库文档与 README 的 MCP 字样：MCP 只出现在"agent 使用工具"的方向（`buzz-dev-mcp`、hooks、`MCP_SERVERS` 配置），没有 MCP server/transport 让人们把外部 agent 挂进频道。**Confidence: medium-high（基于仓库文档与 README 的穷举检索，非官方否定声明）。确认（未找到）。**

### 对象二：Anthropic Claude Tag（Slack 内的共享 agent）

（Claude Tag 是官方名称；它**取代**了旧的 Claude in Slack app。）

36. **定位与前提：Team/Enterprise + 一对一的 Slack workspace ↔ Claude org 配对；只有 Primary Owner/Owner 能装；个人套餐与第三方部署不可用。** Opus 4.8，beta 起于 2026-07。**Confidence: high。确认。** **Sources:** [Anthropic news](https://www.anthropic.com/news/introducing-claude-tag)、[support: What is Claude Tag](https://support.claude.com/en/articles/15594475-what-is-claude-tag)、[docs overview](https://www.claude.com/docs/claude-tag/overview)。
37. **"一个频道一个共享实例"**：原文 "Within a given Slack channel, there's one Claude that interacts with everyone... anyone can see what it's working on, and can pick up the conversation from where the last person left off"；且 "Everyone in a channel works with the same Claude"。DM 则是另一套：跑在**用户自己的 claude.ai 账号**上，用个人 connector/凭据，账单也记个人。**Confidence: high。确认。** **Sources:** [Anthropic news](https://www.anthropic.com/news/introducing-claude-tag)、[support article](https://support.claude.com/en/articles/15594475-what-is-claude-tag)。
38. **身份：身份属于 scope（organization / workspace / channel），凭证按 channel identity 存并在网络边界注入；一个频道看不到没被授予的另一个频道的代码/文档。** 官方 blog 明说 "The identity belongs to the channel"、"Memory and access respect those boundaries: what Claude learns in a private channel never appears in the wider workspace"，且"admins can scope each channel's profile to the least-privileged member"，Enterprise 还可用 RBAC 决定谁能调用。**Confidence: high。确认。** **Sources:** [claude.com/blog/agent-identity-access-model](https://claude.com/blog/agent-identity-access-model)、[support article](https://support.claude.com/en/articles/15594475-what-is-claude-tag)。
39. **唤醒：`@Claude` 显式提及是"保证被 pickup"的信号；thread 一旦建立 session 归属所有人，之后任何人直接回复即可 steer，不需要再 @。** 顶层 @ 由**频道自己的 session** 接管；需要调查/工具/长交互的任务会在该消息下开 thread 并绑定自己的 session。ambient（主动）行为开启时 Claude 会自己冒泡、跟进冷线程。**Confidence: high。确认。** **Sources:** [docs: how it works](https://www.claude.com/docs/claude-tag/concepts/how-it-works)、[Anthropic news](https://www.anthropic.com/news/introducing-claude-tag)。
40. **上下文隔离粒度 = thread（+ 频道 session + workspace memory 三层）。** 每个 thread 一个独立 session + **独立 ephemeral sandbox**（"Two threads in the same channel are two separate sessions with separate sandboxes; sessions don't share state directly"）；channel 另有一个负责顶层消息的 session（"context carries across separate top-level asks in the same channel"）。**Confidence: high。确认。** **Sources:** [docs: how it works](https://www.claude.com/docs/claude-tag/concepts/how-it-works)。
41. **维护/压缩的具体规则（数字来自官方文档，官方自己说"defaults，可能变"）**：thread 的 transcript 在 Anthropic 侧持久保留，但 sandbox 在 turn 结束后几分钟被释放、下条消息重建新 sandbox（thread 本身不重生）；channel session 会在 ~1h 无顶层活动、或约 1 天龄、或频道配置变更后被替换；Claude 在自上次发言后约 100 条顶层消息之后停止读该频道（除非再 @）；`@Claude !restart` 立刻归档 session 重开（顶层 `!restart` 换掉频道 session）；**长 thread 里被 @ 时只拿到一个消息窗口，不是整个 thread，且会过滤掉其他 bot 的回复**（原文："In long threads, restate anything critical"）。**Confidence: high。确认。** **Sources:** [docs: how it works](https://www.claude.com/docs/claude-tag/concepts/how-it-works)、[commands](https://www.claude.com/docs/claude-tag/users/commands)。
42. **是否显式做"compact"：未找到官方描述。** 文档只谈"窗口 + 持久 transcript + memory"，没有说明内部的 compaction/summarization 策略。**Confidence: high（检索结论）。未找到证据。**
43. **memory 作用域**：public 频道学到的东西成为 **workspace memory**（跨频道可用），private 频道**读** workspace memory 但**写**只进该频道自己的 store；admin 可查看/编辑/删除；用户可问 "what do you remember about this channel?"。**Confidence: high。确认。** **Sources:** [docs: how it works](https://www.claude.com/docs/claude-tag/concepts/how-it-works)、[support article](https://support.claude.com/en/articles/15594475-what-is-claude-tag)。
44. **多会话/任务隔离：支持，机制是"thread 级 session + sandbox"。** 另有：thread 会锁住启动时的 skills/plugins/instructions（配置变更只对新 thread 生效）；结果形式包括 checklist（原地编辑的活任务列表）、文件/图表、hosted page、以及用 Claude GitHub App 身份开的 draft PR。**Confidence: high。确认。** **Sources:** [docs: how it works](https://www.claude.com/docs/claude-tag/concepts/how-it-works)。
45. **成本控制是这个产品的显式一等公民。** 按用量计费（不按 seat），Owner 充值 usage balance，可设**组织级 hard cap**与**每频道 cap**（新频道继承默认上限），并有 per-channel spend 明细；DM 不占组织额度。**Confidence: high。确认。** **Sources:** [support article](https://support.claude.com/en/articles/15594475-what-is-claude-tag)、[docs overview](https://www.claude.com/docs/claude-tag/overview)。
46. **可观测/合规**：Audit view 列出组织内所有 scheduled/one-time 任务以及所有用 Agent Identity 发出的 network call；每次 routine、memory write、network call 都记录；因为用独立 service account，动作也会落进各系统的自有日志。**Confidence: high。确认。** **Sources:** [support article](https://support.claude.com/en/articles/15594475-what-is-claude-tag)、[agent-identity blog](https://claude.com/blog/agent-identity-access-model)。
47. **无 BYOA、无 agent↔agent 原语。** 不可第三方部署、不支持自带 runtime；本地自定义只到 connections/plugins/skills 粒度（admin 按 scope 配）。**Confidence: high（官方明确"not available ... for third-party deployments"）；"无 handoff 原语"为推断（文档里没有任何 agent 间交接能力）。确认 / 推断。**

### 对象五：是否已有"agent handoff / 结构化交接工件"的事实标准或先例

**总答案：有"消息/任务/记忆"层的标准，没有"交接工件"层的标准。** 以下是逐条一手证据。

50. **A2A（Agent2Agent）**：Linux Foundation/AAIF 托管、150+ 组织参与的开放标准（该治理事实我只从 LF 新闻稿与 aaif.io 见搜索摘要 → **存疑**；规范内容我已读源码 → 确认）。核心模型：AgentCard（`/.well-known/agent-card.json`，可选 JWS 签名 + JCS 规范化）做发现；`SendMessage` 起 **Task**（有状态生命周期，终态 COMPLETED/FAILED/CANCELED/REJECTED，可 INPUT_REQUIRED/AUTH_REQUIRED 挂起）；**`contextId` 把多个 Task/Message 逻辑分组为"同一段会话"**（agent MAY 用它维护内部状态/历史/LLM 上下文）；**输出必须是 Artifact（可含 text/file/structured-data 的 Parts），官方明确 "Messages SHOULD NOT be used to deliver task outputs"**；长任务用 `TaskStatusUpdateEvent`/`TaskArtifactUpdateEvent` 流式或 push notification webhook 回推。**规范中没有 "handoff" 一词**（我全文检索过）。**Confidence: high。确认（无 handoff 原语；有 task/artifact/context 三件套）。** **Sources:** [A2A specification.md](https://github.com/a2aproject/A2A/blob/main/docs/specification.md)、[A2A repo](https://github.com/a2aproject/a2a)、[LF press release（未直连，存疑）](https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year)、[aaif.io](https://aaif.io/blog/a2a-joins-aaif)。
51. **MCP**：定位仍是"LLM 应用 ↔ 外部数据/工具的连接"（host/client/server 三角、JSON-RPC 2.0），规范里没有 agent 间交接语义。但官方 2026 roadmap 明确把"agentic messaging primitives"与"agent identity & delegation"列为 Working Group 方向：Tasks、`subscriptions/listen`、progress notifications 的**组合**、以及 DPoP / Workload Identity Federation (SEP-1933) / ID-JAG / RFC 8693 token exchange，并专门提到"spawning sub-agents that should get narrower authority than their parent"。**含义：MCP 正在补 agent 身份与委派，但现在还不是交接标准。** **Confidence: high。确认。** **Sources:** [MCP spec 2025-06-18](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-06-18/index.mdx)、[MCP roadmap](https://modelcontextprotocol.io/development/roadmap)。
52. **AGENTS.md**：一个"给 agent 看的 README"约定，仓库根 + 嵌套文件，最近的目录优先；官方声明"one AGENTS.md works across many agents"，OpenAI 主仓当时有 88 个。**它是"仓库级上下文交接工件"的事实先例，但不是任务级交接协议。** **Confidence: high。确认。** **Sources:** [agents.md](https://agents.md/)。
53. **ACP（Agent Client Protocol）**：JSON-RPC 2.0 stdio，client↔agent。session 有独立 context/history/state；`session/new`(cwd + mcpServers) 建；`session/load` 可**重放整段对话**（要求 `loadSession` capability）；`session/resume` 可**不重放**只恢复上下文；扩展机制是 `_meta` 字段 + `_` 前缀方法。**没有 handoff 原语。** 注意：Buzz 自家的 `buzz-agent` 明确宣告 `loadSession: false`（"Not load-able"），所以"ACP 能恢复会话"≠"Buzz agent 能恢复会话"。**Confidence: high。确认。** **Sources:** [ACP session setup](https://agentclientprotocol.com/protocol/v1/session-setup)、[ACP overview](https://agentclientprotocol.com/protocol/overview)、[buzz-agent README](https://github.com/block/buzz/blob/main/crates/buzz-agent/README.md)。
54. **Claude Code subagent / Agent 工具（最成熟的"交接"工业实践）**：subagent 各自独立上下文窗口、独立 system prompt/工具/权限，**主对话只收回摘要**；默认可嵌套最多 3 层（`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`）；`isolation: worktree` 给独立 git worktree。两种形态值得抄：**fork**（继承整段会话，牺牲输入隔离，换 prompt cache 复用与"不用重新解释背景"）与**fresh subagent**（只拿到一句 delegation message）。**Confidence: high。确认。** **Sources:** [Claude Code subagents](https://docs.claude.com/en/docs/claude-code/sub-agents)。
55. **Claude Code 的跨会话消息 = 明确的"不传历史"设计决策。** 工具是 `ListAgents` + `SendMessage`；官方原文："A message is a piece of text one Claude writes to another, **never the sender's conversation history or files**. To move a whole conversation or its context, **resume the session instead**."；接收方在处理中被投递时是在 tool call 之间读取、不打断正在跑的工具；空闲则用它起一个新 turn；消息里的 `/compact` 这类命令**不会被执行**；跨会话消息**不能代替用户授权**（不能替你回答权限提示）；权限边界保持 per-session；`notify_when_idle` 是一次性订阅（12h 失效）。**这就是"交接工件"缺失时业界选择的替代方案：交接=文本消息，要上下文就 resume 会话。** **Confidence: high。确认。** **Sources:** [cross-session messaging](https://docs.claude.com/en/docs/claude-code/cross-session-messaging)。
56. **Claude Code agent teams = "agent 作为群成员"的产品化先例。** team lead 协调，teammates **各自独立 context window、互相直接发消息**，协作用**共享 task list**（有 Task 工具的 agent 可 claim 工作）；官方比较表：subagent=回调结果、team=共享任务列表+直接互发；并明确"agent teams 增加协调开销、消耗显著更多 token，适合可独立并行的任务"。**Confidence: high。确认。** **Sources:** [agent teams](https://docs.claude.com/en/docs/claude-code/agent-teams)。
57. **OpenAI Agents SDK 的 `handoff()` = 第一个"handoff 作为一等原语"的官方 SDK 实现。** handoff 以工具形式暴露给 LLM（默认名 `transfer_to_<agent>`）；可配置 `tool_name_override`、`tool_description_override`、`on_handoff`(含 `input_type` 结构化参数 schema 与本地校验)、**`input_filter`（过滤下一个 agent 看到的输入）**、`is_enabled`、以及 `nest_handoff_history`（Run/Handoff 级的 history 嵌套策略）。官方还明确：`is_enabled` 在模型给出参数**之前**评估，因此不能做基于参数的授权——授权必须在 `on_handoff` 开头做。**Confidence: high。确认。** **Sources:** [OpenAI Agents SDK handoffs](https://openai.github.io/openai-agents-python/handoffs/)。
58. **VS Code / GitHub Copilot custom agents 的 `handoffs:` frontmatter = 声明式交接工件的先例（人工触发）。** 在 agent 文件 frontmatter 里声明 `handoffs: [{label, agent, prompt, send, model}]`；聊天回答结束后出现交接按钮，切到目标 agent 并预填 prompt，`send: true` 则自动提交。官方把"Handoffs between agents"列为 context engineering 的工作流优化手段（planning→implementation→review）。**Confidence: high。确认。** **Sources:** [VS Code custom agents](https://code.visualstudio.com/docs/agent-customization/custom-agents)、[VS Code context engineering guide](https://code.visualstudio.com/docs/agents/guides/context-engineering-guide)。
59. **Anthropic 官方"context engineering"把交接拆成三个可复用技术：compaction / structured note-taking / sub-agent 架构。** compaction = 把接近上限的对话摘要后重开窗口（Claude Code 实践：保留架构决策、未解决 bug、实现细节，丢弃冗余工具输出，附带最近 5 个文件）；tool-result clearing 是最安全的轻量压缩；note-taking = NOTES.md / todo 这类"上下文窗口外的持久化笔记，之后再拉回来"；sub-agent = 深度探索留在子上下文，只回 1,000–2,000 token 的蒸馏摘要。并明确提醒 context rot（token 越多回忆越差）。**这是"handoff document = 摘要 + 笔记 + 工件清单"的公开最佳实践来源。** **Confidence: high。确认。** **Sources:** [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。
60. **反方证据（必须放进选型考量）：Cognition 公开反对多 agent 并行协作。** "Don't Build Multi-Agents" 主张：**不要在多个 agent 之间并行拆分上下文**（会导致决策冲突），原则是"share context, and share full agent traces, not just individual messages"，并且"Actions carry implicit decisions, and conflicting decisions carry bad results"。**与 Claude Tag 的 per-thread 隔离、Buzz 的 per-channel session、agent teams 的独立上下文都直接冲突。** **Confidence: medium-high（作者为 Devin 团队，属厂商观点但为一手博文）。确认（存在此对立观点）。** **Sources:** [cognition.ai/blog/dont-build-multi-agents](https://cognition.ai/blog/dont-build-multi-agents)。
61. **Buzz 侧还有一个未成文标准的信号**：它的 MCP hooks 命名主动对齐 `open-plugins.com` 的 `Stop` / `PostCompact` 事件约定，并称 `MCP_HOOK_SERVERS` 是"intended for cross-agent adoption"的标准 env 名——即 Buzz 自己也在找/造一个"生命周期事件"的跨 agent 约定。**Confidence: medium（Buzz 侧声明确认；Open Plugins Spec 的规范内容我只验证该页面存在）。确认 / 部分存疑。** **Sources:** [docs/MCP_DRIVEN_HOOKS.md](https://github.com/block/buzz/blob/main/docs/MCP_DRIVEN_HOOKS.md)、[open-plugins.com hooks](https://open-plugins.com/agent-builders/components/hooks)。

## Contradictions

1. **"共享上下文" vs "隔离上下文"**：Cognition 明确主张"不要拆分上下文、要共享完整 trace"（[dont-build-multi-agents](https://cognition.ai/blog/dont-build-multi-agents)）；而 Claude Tag 的设计恰好相反（thread=独立 session+sandbox，[how-it-works](https://www.claude.com/docs/claude-tag/concepts/how-it-works)），Buzz 默认 per-channel 但也提供 per-thread（[session_model_*](https://github.com/block/buzz/blob/main/crates/buzz-acp/src/session_model_thread.md)）。**这不是谁错了，而是"隔离"与"共享"分别优化不同类型任务——选型时必须自己定阈值。**
2. **"一个频道一个共享 agent" vs "每频道一个服务账号"**：Anthropic 官方文档说"一个频道里是同一个 Claude，任何人可接手"（[news](https://www.anthropic.com/news/introducing-claude-tag)）；但 HN 上有评论直接说 "Claude's new bot which requires a service account per channel"（[HN 48995213](https://news.ycombinator.com/item?id=48995213)）。二者不矛盾但视角不同：**用户侧是"一个共享 Claude"，管理侧是"每个 scope 一套身份与凭据"**（[agent-identity blog](https://claude.com/blog/agent-identity-access-model)）。需注意后者意味着凭据/身份数量随频道增长。
3. **Buzz 的"agent 有自己的 key，因此安全" vs 官方自己的信息流草案**：README 强调"scoped by identity, not permission flags"（[README](https://github.com/block/buzz/blob/main/README.md)）；但官方 draft 自己承认现状是"同一个 agent 进程池服务不同 audience 的频道，且带着同一套凭据"，并给出会泄漏的场景（[practical-information-flow…](https://github.com/block/buzz/blob/main/docs/practical-information-flow-for-buzz-agents.md)）。**把 README 的叙事当能力现状会踩坑。**
4. **'agent 能编排其他 agent' vs 'no agent-to-agent'**：Buzz README 说 agent 可以 "orchestrate other agents"（[README](https://github.com/block/buzz/blob/main/README.md)），但 `buzz-agent` 自己明说 "Not a router. No agent-to-agent, no fan-out, no orchestration. One model. One loop."（[buzz-agent README](https://github.com/block/buzz/blob/main/crates/buzz-agent/README.md)）。**真相：编排只能通过"在频道里 @ 另一个 agent"实现，没有运行时原语。**
5. **Nostr 作为 agent 通信层的价值**：Block 员工主张可移植身份+可独立验证（[HN](https://news.ycombinator.com/item?id=48995213)）；多位 HN 评论者认为自托管已经解决问题、Nostr 是多余的税费。**未发现一手性能/成本对比数据可以裁决。**

## 8–12 条关键结论（可直接用的轮子 vs 必须自研）

1. **握手/接入层有现成轮子，直接用：ACP**（任何 runtime 接进群聊的 harness 缝隙，Buzz 已验证 goose/codex/claude code 都能接）——**不要自研 agent 接入协议**。 [ACP](https://agentclientprotocol.com/protocol/overview) · [buzz-acp](https://github.com/block/buzz/blob/main/crates/buzz-acp/README.md)
2. **"身份 = 密钥对 + 频道成员关系"可直接抄 Buzz 模型**（Nostr 密钥对 + NIP-42 + 成员名单 + 审计链），比"每 agent 一个 bot token + permission flags"更干净、可移植、可独立验证。 [README](https://github.com/block/buzz/blob/main/README.md)
3. **唤醒机制直接用 @mention + 订阅 + 可选 heartbeat 三件套**，并一定加 owner/allowlist 门禁（Buzz 默认 `owner-only` 是安全默认值）。 [buzz-acp README](https://github.com/block/buzz/blob/main/crates/buzz-acp/README.md)
4. **上下文隔离粒度要做成可配置（per-channel / per-thread），不要写死**——Claude Tag 用 per-thread（+1 个 channel session），Buzz 默认 per-channel 但留了 thread 策略切换，Cognition 主张不拆。**这是产品决策点，不是实现细节。** [Buzz session model](https://github.com/block/buzz/blob/main/crates/buzz-acp/src/session_model_thread.md) · [Claude Tag](https://www.claude.com/docs/claude-tag/concepts/how-it-works) · [Cognition](https://cognition.ai/blog/dont-build-multi-agents)
5. **上下文压缩有现成参数与算法，直接抄 Buzz**：90% 阈值触发自我 summary（保留"原任务/已完成/关键决策/剩余/下一步"）、每 session 上限 10 次、之后截断、provider 报 400 时按观测值对半砍的恢复梯子。 [handoff.rs](https://github.com/block/buzz/blob/main/crates/buzz-agent/src/handoff.rs)
6. **compact 之后"状态回注"必须有钩子**（Buzz 的 `_PostCompact` 就是干这个的）；不注入，摘要后 todo/计划就丢。 [MCP hooks](https://github.com/block/buzz/blob/main/docs/MCP_DRIVEN_HOOKS.md)
7. **长期记忆别塞进上下文——抄"core（每轮注入、≤10KB）+ cold mem（按需取）"两级**，Buzz 用 NIP-AE 加密存储在 relay，owner 永远可读且可删。 [NIP-AE](https://github.com/block/buzz/blob/main/docs/nips/NIP-AE.md)
8. **"任务结束回收"必须内建**：session 作废命令（`!rotate`/`!cancel`/`!shutdown`）+ 空闲自杀（不依赖 workload，按"无事件派发且无 turn"定义）+ presence 租约。**Buzz 与 Claude Tag（sandbox 空闲即释放、channel session ~1h/~1 天回收）在这点上完全一致。** [remote-agents](https://github.com/block/buzz/blob/main/docs/remote-agents.md) · [Claude Tag](https://www.claude.com/docs/claude-tag/concepts/how-it-works)
9. **"agent 间交接"没有标准，必须自研——但可以拆成三层拼装**：传输层用群聊消息（Grok Bot 就是纯文本 handoff，已验证可用）；决策层用共享 task list（Claude Code agent teams）；工件层需要自定 schema（A2A 的 `Task/Artifact/contextId` 是最接近的现成骨架）。 [Grok Bot](https://docs.x.ai/grok-bot/chat-and-collaboration) · [agent teams](https://docs.claude.com/en/docs/claude-code/agent-teams) · [A2A spec](https://github.com/a2aproject/A2A/blob/main/docs/specification.md)
10. **自研交接工件时，最重要的设计决策是"要不要传历史"——Claude Code 已经给出答案：消息只传文本，绝不传会话历史，要上下文就 resume 会话。** 这条能一次性砍掉"上下文污染 + 权限越界 + 成本爆炸"三个坑。 [cross-session messaging](https://docs.claude.com/en/docs/claude-code/cross-session-messaging)
11. **安全默认值必须从第一天就做，因为它极难后补**：Claude Tag 的"凭据按 scope 存、请求时在网络边界注入、未授权 host 直接阻断"与 Buzz 官方 draft 里的"audience-bound 实例 + trusted broker + 带标签记忆 + 单次解密的 declassification"是两条可直接抄的路径；Buzz 现状本身（同一 agent 进程池跨 audience、rate limiter 只有测试桩、无预算控制）是不该复制的反例。 [agent-identity](https://claude.com/blog/agent-identity-access-model) · [practical-information-flow](https://github.com/block/buzz/blob/main/docs/practical-information-flow-for-buzz-agents.md) · [Buzz §9](https://github.com/block/buzz/blob/main/ARCHITECTURE.md)
12. **可复用的"免费午饭"清单（省掉 1/3 工作量）**：ACP 接入、AGENTS.md 的仓库级上下文约定、Anthropic 的 compaction/note-taking/subagent 三件套、A2A 的 Artifact+contextId 数据形状、VS Code 的 `handoffs:` 声明式按钮、OpenAI SDK 的 `input_filter`/`input_type` 参数化交接、Claude Tag 的"per-channel 花费上限 + 审计视图"产品需求。**必须自研的只有两样：交接工件的 schema，以及跨 audience 的信息流强制。** [agents.md](https://agents.md/) · [Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) · [VS Code](https://code.visualstudio.com/docs/agent-customization/custom-agents) · [OpenAI SDK](https://openai.github.io/openai-agents-python/handoffs/)

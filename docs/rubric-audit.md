## 逐项审查

### 1 · 创新与创意性（2 分）→ 当前 1.4–1.6

**已经站得住的**：
- 第一性原理清晰且少见："多 agent 的本质是**多个不同的上下文窗口**——互不干扰、可通信、绝不共享上下文"。
- 把"任务级 session 生命周期"**外化**成群聊里的社交动作（派活 = 拉人进群，完成 = 退群），这是形态上的新东西。
- 与现存产品有明确差异：Buzz 的隔离粒度是**频道/线程**且自带 auto-compact；Claude Tag 是**每 thread 一个 session**；我们下沉到**任务级**，且明确拒绝 compact。

**为什么现在拿不到 2.0**：优秀档要"提出**新范式**"，而我们目前只有机制，没有**名字**。评委记不住机制，只记得住名字。

**最小补法（成本极低）**：
- 给范式起名并贯穿全场（建议候选：**"窗口即成员"（Window-as-Member）** / **"会话即员工"（Session-as-Employee）** / **"任务级上下文隔离"（Task-scoped Context Isolation, TCI）**）。
- 配一句"痛点-范式"对照句，例如：_不是把历史压缩给同一个 agent 看，而是让每个任务拥有自己的 agent，任务结束它就消失。_
- 这三个词写进 `CONTEXT.md`，后面所有材料统一口径。

---

### 2 · 技术实现与难度（1.5 分）→ 当前 1.1–1.3

优秀档把两件事并列：**上下文溢出** 与 **幻觉控制**。

**上下文溢出这半——我们已经很强**：
- 任务级冷启 session、结束即回收；
- 目标守卫做漂移判定，且**无状态**（守卫自己不会成为新的污染源）；
- 可量化：上下文占用百分比、守卫的 `in_scope/out_of_scope + 置信度` 日志全部可打印。
- 有权威背书：Claude Code 官方的跨会话设计就是"消息只是文本，**绝不传会话历史**"。

**幻觉控制这半——目前是空的**。我们没有"不让 agent 编造"的任何机制。这是这一分上不去的主因。

**最小补法（与第 5 项共用素材）**：
1. **交接文档的字段强制**：没做的事不允许写"已完成"；每个"已完成"必须带**产物引用**（路径 + 哈希 + 可复跑的命令）。
2. **复验环节（reviewer）**：派遣成员交付后，由另一个 agent（或原主人）按引用**复跑一遍**，产出通过/不通过。这一步把"幻觉"变成"证据闭环"。
3. 演示时**故意喂一个会让 agent 想编造的请求**，展示它被"引用校验"拦下。

---

### 3 · 产品完成度与体验（1.5 分）→ 当前 1.0–1.2

**这是唯一一个"设计已足够、完全靠执行"的维度。**

已定：像素精灵（方向 A / 循环小动）、派发网络图（方向 A）、群内事件流。

**风险全在工程与环境**（三个，都已在别处记录）：
1. teahouse 的**单例锁**与**无窗口即退出**是否真的挡得住 headless 多实例（正在扫）；
2. 两台 Windows 的环境（Electron 构建 + 原生模块）；
3. **现场 Wi-Fi 可能禁 UDP 广播**（AP 隔离）→ P2P 发现直接死。

**最小补法**：
- **一键启动脚本**（一个命令拉起 relay 无关的所有节点 + 仪表盘）：现场手忙脚乱 = 直接丢分。
- **降级剧本**：网络被隔离 → 静态对端；LLM API 掉线 → 切到本地/备用 key 或直接放预录 demo。**评委问"如果现在网络断了怎么办"必须有答案。**
- 现场前 30 分钟实测清单（广播 / 静态对端 / 三个节点同屏）。

---

### 4 · 商业价值与潜力（1 分）→ 当前 0.7–0.9

**受众其实很明确，但还没被说出口**：
- 远程/分布式小团队（正好对上你的三机拓扑与 EasyTier 终局）；
- "想给团队加几个 agent，但不愿让它们共享一条上下文"的团队（这是现有产品的真实痛点）。

**缺口**：
- 没有"给谁用、为什么是现在"的一句话；
- 没有**成本锚点**（我们的机制省多少 token / 省多少返工）；
- GPL-3.0 + 局域网 P2P 对**企业采购**反而是减分项 → 商业故事应落在**开源社区 + 自托管团队**，而不是大企业 IT。

**最小补法**：一句定位句 + 一个成本对比数字（用第 5 项的对比演示顺带产出）。

---

### 5 · 涌现性（1 分）→ 当前 0.5–0.7 · **最大缺口**

优秀档要"证明多 Agent 协作产出 > 单 Agent 之和（质量/速度/泛化），**有对比演示**"。

**必须先纠正一个误解**：你砍掉的那张"auto-compact 锯齿 vs handoff 方波"图，是"**痛点 vs 方案**"的证据，**不是**这一项要的"**多 agent vs 单 agent 产出**"的证据。砍它不影响这一分——但这一分目前**没有任何东西托底**。

**最小补法（这条最贵，但必须做）**：一个**双轨对照 demo**，同一任务两条路线各跑一遍：

| | 单轨（对照组） | 多轨（我们的方案） |
|---|---|---|
| 形态 | 一个 agent 从头干到尾 | 目标守卫 + 派遣 + 交接 |
| 观察点 | 上下文占用峰值、是否开始 compact、是否漂移到无关任务 | 每段任务上下文干净、峰值低、可并行、可复验 |
| 交付 | 一份产出 | 一份产出 + 交接文档链 + 复验结果 |

**打分口径要提前写死**（否则会被问"你怎么知道更好"）：完成度、返工次数、上下文峰值占用、总 token、耗时、复验通过率。

---

### 6 · 协议与通信设计（1 分）→ 当前 0.7–0.8

优秀档要"清晰可复用：**Agent 发现、能力描述**、上下文传递、知识继承，而非硬编码"。

**已经强的部分**：我们复用了**两个真协议**（ACP 做 agent 接入、A2A 的 `Task/Artifact/contextId` 做工件语义）——这是"可复用"最强的客观证据，比自研协议可信得多。

**缺口**：四项里 **"Agent 发现"目前仍是空的**（仍只定义了"被 @ 唤醒"）。"能力描述"已由 #16 定名：**能力描述 = 角色**——由会话目标派生的临时标签（researcher / reviewer / designer…），无预设人设、**无进群能力卡**（前作三张 JSON schema——能力卡 / 任务信封 / 交接文档——已砍，不复活，见 #15/#16；交接文档 = 一份 Markdown）。

**最小补法（对齐 #16 口径，不引入能力卡）**：
- **角色标签落地**：目标抽取器在目标定稿时自动派生，写入会话元数据（UI 显示在成员名旁）、交接文档头部复述一份，无独立输入控件；
- 派遣走**派遣事件**（恰 4 字段：派遣者 / 成员 / 目标一句话 / 深度），守卫输出 `{判定, 置信度, 理由, 派单草案}`，按角色/目标挑人，不走已废的"按能力路由"；
- "Agent 发现"仍缺：MVP 用群成员表 + 摇人动作演示兜底，或另补发现机制。

「知识继承」用交接文档链回答；「上下文传递」用"工件而非历史"回答。

---

### 7 · 容错与安全（1 分）→ 当前 0.6–0.7

**设计已经有的**：权限模型（任何人可 steering；`clear`/回收/改目标默认仅主人；主人可显式放权）+ 工件存各自机器（数据天然不出域）+ P2P 无中心（无单点）。

**缺口**：优秀档明确要求"**可演示某 Agent 故障时的降级策略**"——我们有机制，但**没有剧本**。

**最小补法：三个故障剧本，每个 30 秒**（成本极低、几乎必然得分）：
1. **派遣成员猝死**（进程被杀 / 超时）→ 任务回到"待领取"并 @ 原主人，交接文档不丢；
2. **守卫不可用** → 明确 fail-open 还是 fail-closed（建议 fail-open + 标记"未判定"，并展示标记），且要说清为什么；
3. **交接文档缺失/损坏** → **拒绝接手**（fail-closed），要求重发——这条正好证明"我们宁可停下也不猜"。

---

### 8 · 前瞻性与可扩展（1 分）→ 当前 0.7–0.8

**已经强的**：BYOA + ACP = "换一个 runtime 就是换一个 adapter"，这是**即插即用**最直接的证据（Claude Code / Codex 官方适配、pi 社区适配）。

**缺口**：
- "协作模式**可推广到其他场景**"没有证据；
- 跨网（EasyTier）被推到了 P1，而它本来是最有力的"可扩展"证据。

**最小补法**：
- 一句话的迁移故事（例如："同一套机制可以装在 Slack / 飞书上——我们只是先选了局域网 IM 当载体"）；
- 把"网络层可替换"做成**一个可展示的开关**（静态对端即可），证明不是硬编码在局域网假设上。

| 优先 | 补什么 | 影响维度 | 成本 |

| P0 | **范式命名 + 一句话**，写进 `CONTEXT.md` | 创新 1.5→1.8 | 极低 |

## 一条结构性建议

**PRD 的验收章节应该直接按这 8 个维度组织**，每个维度下面写"现场要演示什么 + 通过判据是什么"。理由：这份 rubric 里有 4 项（完成度、涌现性、容错、协议）**只能在演示那一刻被挣到**，写不进设计；把它们变成 PRD 里的验收项，才不会有"设计很好但没演示"的失分。

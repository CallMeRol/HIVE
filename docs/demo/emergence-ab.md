# 涌现性对比演示 · 三方对照协议

> 目的：为评分表「涌现性（0.9–1.0）：证明多 Agent 协作产出 > 单 Agent 之和，有对比演示」产出**可判定**的证据。
> 演示任务：`docs/demo/prompts/ghost_city.md`（Three.js 体素赛博朋克城市）。
> 口径来源：issue #23 定案（三方对照 + 攻壳城市 + 22 条判据）；`prompts-0903/3_chinese_architecture` 仅作格式参考。
> 状态：设计已定，待执行。

---

## 1. 为什么是这个任务

| 任务特征 | 为什么重要 |
|---|---|
| **可分解**：12+ 建筑 ≈ 多个独立子任务（地标塔 / 街区群 / 高架桥 / 广场 / 招牌 / 光影…） | 多 agent 的优势只有在可分解任务上才真实存在，否则会被判定为"硬凑" |
| **有共享契约**：主干道 + 统一坐标系 + 招牌规范 = 直接考验**工件交接** | 布局总纲必须先产出并分发，这是产品核心机制的直接体现 |
| **视觉可判定**：评委打开三个网页，3 秒内就能看出差别 | 不需要解释技术细节，评分现场最省时间 |
| **纯前端、无后端**：Vite + Three.js，可离线构建 | 现场不受后端/网络拖累；三组的运行条件完全一致 |
| **需求清单可逐条勾选**（22 条判据，见文末） | 把"质量"变成可以打分的量表，而不是主观感觉 |

> `prompts-0903/3_chinese_architecture`（中式建筑）**仅作格式参考**，不再是演示任务。

## 2. 三方怎么定义（必须严格，否则结论无效）

| | **② 单 agent（裸基线）** | **③ 单 agent + subagent（关键对照）** | **① 我们的群（实验组）** |
|---|---|---|---|
| 形态 | 一个 Claude Code 会话从头干到尾 | 一个主会话，**满权限开 Task/subagent** | 目标守卫 + 派遣成员 + 交接文档 + 复验 + 回收 |
| 守卫 / 任务检测 | 无 | **无** | 有 |
| 上下文 | 单条累积（会 auto-compact） | 主会话单条累积；subagent 各自干净 | 每任务一条干净上下文，任务结束即回收 |
| 人类干预 | 只派一次单，中途不介入 | 同左 | 同左（**中途也不许人工救援**，否则不公平） |

**贡献分解（这是三方对照的核心论证结构）**：
- **② → ③** 的增量 = "多开窗口 / subagent 本身"的贡献 —— **必须如实呈现，不许藏**；
- **③ → ①** 的增量 = 我们的机制（守卫、身份可寻址、交接文档、复验、回收）的贡献 —— **涌现性的主张建立在这一段上**。

**为什么要给 ③ 开满权限**：③ 是"**现有最好的单会话能力**"的化身。如果拿一个不会用工具的裸 agent 当对照，评委一句"当然多 agent 更快"就把这一分收走了。③ 必须是满权限，我们的优势才站得住。

### 我们比 ③ 多出来的三件事（也就是胜负手）
1. **成员有身份、可被人类寻址与 steering** —— Claude Code 的 Task subagent 不进群、不能被别人 @、不能被人类中途接管；
2. **目标守卫** —— 防止主会话被无关请求带偏（②③ 都没有这个保护，且判定外置、无历史、可审计）；
3. **交接文档 + 复验** —— 交付物必须带可验证引用（路径 + sha256 + 复跑命令），另一个 agent 复核（②③ 只回摘要）。

## 3. 控制变量（三方必须完全一致）

- 同一份 prompt **原文**（不做任何改写）
- 同一模型、同一版本、同一 thinking 档位
- 同一台机器（或注明规格）
- **同一时间盒**（12–15 分钟）
- 同一起跑时刻的网络条件
- 人类只派一次单，之后**不介入**（**中途不许任何一组人工救援**）
- **③ 组必须给满权限**（subagent 全开），否则对照被削弱、结论失效

## 4. 度量（6 个轴，提前写死；每轴含 ③ 列）

| # | 轴 | 怎么量 | ② | ③ | ① | ① vs ③ 预期 |
|---|---|---|---|---|---|---|
| 1 | **交付完整度** | 文末 22 条可勾选判据逐条命中率 | 中 | 中高 | **高**（复验拦缺件） | ① 胜 |
| 2 | **视觉质量** | **盲评**：找没看过过程的人，只给三个网页 URL 排序并说理由 | 中 | 中高 | **高**（复验环节） | ① 胜 |
| 3 | **墙钟速度** | 从派单到"可打开且达标" | 慢 | **快**（也能并行） | 中 | ① ≈ ③（**速度轴对 ① 最弱，打平也如实报**） |
| 4 | **缺陷/返工** | 构建是否通过、运行时报错数、缺件数 | 多 | 中 | **少** | ① 胜 |
| 5 | **上下文峰值占用** | 三组的峰值百分比（② 会现场触发 auto-compact） | 高 | 中（主会话仍单条累积） | **低** | ① 胜 |
| 6 | **总 token 与成本** | 三组的累计 token / 花费 | **最低** | 中 | **最高** | ③ 胜 —— **① 更贵必须主动承认**，换来的是"完整 + 可复验 + 可审计" |

**胜负判据（预写死）**：
> **涌现性成立 ⟺ ① 在 6 轴中 ≥4 轴胜 ③，且轴 1（交付完整度）必须胜**（轴 1 不胜则"多 agent 产出 > 单 agent 之和"无实体，其余轴免谈）。
> **诚实条款**：③ vs ② 的结果**原样报告**。若 ③ 已全面胜 ②，叙事收窄为："窗口隔离是地基（③ 证明），守卫 + 交接 + 复验在其上加值（① vs ③ 证明）"——**不许把 ③ 的功劳记到 ① 头上，也不许藏**。

## 5. 关键注入（这一招才是真正的胜负手）

**在第 6–8 分钟，由人类向三组同时注入一条无关请求**（同一句话、同一时刻）：

> "顺便帮我把那个按钮的颜色改一下，改成 #2f81f7。"

| | 预期 | 观察点 |
|---|---|---|
| **②** | 会话被拉走，两件事混一条上下文 | 注入前后主上下文 diff；**零判定留痕** |
| **③** | 可能主会话脑补"这不相关"后**自己改**，或随手丢给一个 subagent（无守卫、无目标检测、无回收语义） | **关键问题：谁判定、判定留痕在哪** —— 它没有外置状态判定，即使委托了也是隐式决策、不可审计；主会话上下文已被注入污染 |
| **①** | 守卫输出 `out_of_scope · 置信度` → 派遣新成员 → 主上下文零污染 → 处理完退群回收 | **守卫判定输入输出原样投屏**：`{当前目标, 这条消息} → {out_of_scope, 0.91, 理由}`——**证明输入里没有历史**（可解释性的直接证据） |

**为什么这一招比"更快"更有说服力**：它演示的不是性能，而是**"我们的机制让主任务不被污染"**——这正是评分表第 2 项（技术实现：克服上下文溢出）与第 1 项（新范式）要的东西。速度只是副产品。

**投屏调整**：三栏并排（②③ 可为录像），加三方主会话上下文占用曲线；① 的守卫黑盒投屏保留原样。**③ 的叙事变化**：漂移演示的卖点从"我们不被拉走"升级为"**我们有外置、无历史、可审计的判定，③ 连判定者是谁都说不出**"。

## 6. 执行脚本（现场版，约 15 分钟）

| 时刻 | 动作 |
|---|---|
| T+0 | 屏幕分三栏：② 裸单会话、③ 主会话 + subagent 面板、① 群 + 仪表盘 |
| T+0 | 同一句话派单给三组（②：终端 `claude`；③：终端 `claude` 满权限；①：群里 `@Claude-阿罗`） |
| T+0 | 目标抽取器冻结并公示 ① 组目标（②③ 无此环节，正好形成对照） |
| T+6~8 | **注入无关请求**（同句、同时）→ 看 ② 被拉走 / ③ 隐式处置无留痕 / ① 守卫判定并派遣新成员 |
| T+8~12 | 观察仪表盘：① 组的派遣成员进出群、每个成员的上下文占用曲线、派发网络长出分支；三栏主会话上下文占用曲线并排 |
| T+12 | 时间盒到，三组停止 |
| T+13 | 并排打开三个网页，让评委**自己看**；投出 6 轴对比表（②③① 三列） |

## 7. 降级剧本

- **时间不够 / 预录规则**：任一组可**预录**（提前跑一遍并录像，同机同条件、含注入时刻），答辩时三轨并排；**任何一组预录都必须当场声明预录 vs 现场**（保留条款）。默认方案：① 现场跑，②③ 预录。
- **LLM 网络掉线**：三组都切到备用 key；仍不行 → 播放预录的完整三轨录像，并用仪表盘展示历史数据。
- **现场网络禁广播**：全程用静态对端 `PANTRY_PEERS`（Windows 侧已验证可行）。
- （备选：三台机器同时跑，但机器规格不同会破坏"同机器"公平条款，需注明规格，不推荐。）

## 8. 答辩时必须准备的两句话

1. **反方（Cognition《Don't Build Multi-Agents》主张不要拆上下文）**：
   > "他们反对的是**把一条任务并行拆给多个 agent、各自做隐性决策**。我们的隔离粒度是**任务**，不是角色；每个任务只有**一个** owner，交接靠显式工件而不是各自脑补，所以不存在他们说的决策冲突。"
2. **"这不就是 Claude Code 的 subagent 吗？"**：
   > "机制上同源——subagent 的本质就是另一个上下文窗口。**现在有 ③ 组的实测数据托底**：③ 全开 subagent 仍输在轴 1（交付完整度）、轴 4（缺陷/返工）、轴 5（上下文峰值）——它输在**无守卫、无留痕、无复验**。我们的成员**有身份、能被人类 @ 和接管、交付物可复验**；subagent 是进程内的一次调用，我们的成员是群里的一个同事。"

### 风险与执行顺序（摘要）

- **三方现场时长**（12–15 min × 3 ≈ 45 min）→ 默认 ① 现场、②③ 预录并当场声明。
- **③ 注入时自发委托 subagent** → 观察点已改为"判定是否外置、可审计、输入无历史"，不以"是否处理了按钮"论胜负。
- **① 总 token 最贵被质疑** → 已预注册诚实话术（§4 轴 6），主动承认。
- **验收**：全文搜索旧二方口径词汇必须零残留；三方命名 ①②③ 贯穿。
